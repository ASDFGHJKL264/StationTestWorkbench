## 批量验证口径

`WORKBENCH_BATCH_RUNS=1000`：用两个真实 TCP 故障注入对端轮流执行 1000 次独立 SN 测试，每次完整经过预约、发送、终态、数据库提交、归档确认。完成后遍历所有历史页，核对 **1000 个唯一 runId、1000 个 PASS、每个结果3个完整步骤**，并检查总启动次数恰为1000。

这是集成回归次数，不是采样频率，也不是硬件吞吐极限。对端使用1 ms模拟延迟，但 QtTest 轮询、Windows调度、SQLite事务均包含在总耗时中。默认正常演示每步400 ms。

GUI响应探针使用10 ms QTimer，在真实SQLite `BEGIN IMMEDIATE`写锁导致后台提交失败并重试时统计主事件循环的间隔。测试断言最大间隔低于200 ms，报告记录本次观测值；这不是持续运行时任何负载下的硬实时承诺。

## 已修复并加入回归的实际问题

- 客户端重启后，远端尚在执行的 SN 原本可能提前释放：数据库增加恢复占用和部分唯一索引，引擎恢复完整请求后先对账。
- 普通保存失败与工位 unknown 同时出现时，可能提前释放：待存终态优先，只有数据库确认中断后才释放未结算身份。
- 确认丢失、重复终态期间，读取空的可变 JSON 意外插入字段，导致把已完成判定清空：只读身份改为 `.value()`，已归档同一终态直接重发 ACK；冲突回传拒绝覆盖。
- 中断归档失败后，真实迟到终态先提交成功，遗留的中断重试可能覆盖显示：终态成功取消该次中断重试，测试继续等待超过重试周期，确保 PASS 不回退为 UNKNOWN。
